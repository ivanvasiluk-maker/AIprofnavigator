```
  Аргументы: --runs N (по умолчанию 3), --profiles путь (по умолчанию inputs/).
  Для каждого профиля прогнать полную сборку CareerAssessment N раз подряд
  и сравнить результаты между собой по ключевым полям:
    - identity.professional_core (список ролей),
    - routes.recommended_route_id и title рекомендованного маршрута,
    - identity.seniority_current,
    - metadata.recovered_by.

  Отдельно считать долю прогонов, где основной маршрут вышел пустым (значения вида
  "не уточнено", "Возможный маршрут", пустая строка). Это простейший детектор заглушки:
  в реальном отчёте от 20 августа строка "не уточнено" встретилась больше сорока раз.

  Напечатать таблицу: профиль | совпало прогонов из N по каждому полю | recovered_by по прогонам.
  И одно итоговое число: доля профилей, где все N прогонов дали один и тот же
  основной маршрут. Формат строки: "стабильность основного маршрута: 7 из 10 профилей (3 прогона)".
  Результат сохранять в tests/career_profiles/results/stability_<дата>.json.

  Скрипт делает реальные вызовы модели, поэтому: печатать в начале оценку количества
  вызовов (профилей * runs) и требовать подтверждения флагом --confirm, чтобы случайный
  запуск не потратил лишнего.

Критерий приёмки:
  1. python tests/career_profiles/run_stability.py --runs 3 --confirm печатает таблицу
     и итоговое число;
  2. json с результатами сохранён;
  3. без --confirm скрипт ничего не тратит и печатает оценку.
```

## Задание 7. Разбить один огромный вызов на четыре маленьких

*Зачем: настоящее лечение причины. Браться только после заданий 1–6, когда есть чем
померить результат.*

```
Задача: разбить единственный аналитический вызов модели на четыре последовательных
маленьких.

Как сейчас: openai_client.py, build_career_assessment делает ОДИН вызов, который должен
за раз определить профессиональное ядро, seniority, доказательства, ограничения,
8-12 карьерных моделей, из них 3-5 маршрутов, анализ рынка по каждому, три сценария
дохода по каждому, вопросы, выводы и первые шаги. Промпт содержит около 50 правил,
преимущественно запретов, схема — 7150 знаков и больше тысячи полей, выход — примерно
4200 токенов. Модель gpt-4o-mini при таком объёме держит правила выборочно и по-разному
от прогона к прогону. Это и есть источник разброса.

Как должно стать: четыре вызова, каждый со своей маленькой схемой и своей валидацией.
  A. Профиль и идентичность: professional_core, seniority_current, seniority_transition,
     transferable_functions, evidence, constraints, user_choice.
  B. Маршруты: на входе результат A, на выходе 3-5 маршрутов с title, why_it_fits,
     entry_path, risks, evidence_ids. Без рынка и без дохода.
  C. Рынок и доход: на входе A и B, отдельно по каждому выбранному route_id.
  D. Первые шаги и выводы: на входе A, B, C.

Требования:
  - выход каждого вызова не больше примерно 800 токенов; если схема не влезает, дроби дальше;
  - каждый шаг валидируется отдельно существующим валидатором (его логику сохранить)
    и при ошибке переспрашивается ТОЧЕЧНО только этот шаг, а не весь отчёт;
  - итоговый CareerAssessment собирается из четырёх кусков, его схема и внешний контракт
    не меняются: рендереры и HTML остаются как есть;
  - если один шаг провалился окончательно — отчёт всё равно выдаётся, но с честной пометкой,

  - запреты, которые сейчас живут текстом в промпте (не предлагать административную работу
    без доказательств, не психологизировать миграцию и язык, не обнулять уровень) перенести
    в код валидатора как проверки. Промпт должен говорить, ЧТО делать, а не перечислять,
    чего не делать.

Критерий приёмки:
  1. pytest tests -q → 0 failed;
  2. tests/career_profiles/run_stability.py --runs 3 (задание 6) показывает стабильность НЕ ХУЖЕ,
     чем до правки (замер до правки должен быть сохранён);
  3. среднее generation_seconds из аналитики меньше, чем было;
  4. внешний контракт CareerAssessment не изменился, HTML-отчёт выглядит как раньше.
```

## Ещё одно, отдельно: выкат обрывает живые интервью

Это не про качество отчёта, но именно это могло портить ваши тесты с Оксаной.

Состояние диалога хранится в памяти процесса (`bot.py`, `Dispatcher()` без хранилища —
это MemoryStorage). Каждый выкат на Railway перезапускает процесс и сбрасывает всех,
кто в этот момент проходит бота. 20 августа выкатов было шесть за день.

**Быстрое решение прямо сегодня, без кода:** договоритесь не выкатывать, пока идёт
тестовый проход. Одного этого хватит, чтобы результаты тестов перестали «плавать».

**Нормальное решение** — задание для Codex:

```
Задача: перенести состояние диалога из памяти процесса в постоянное хранилище,
чтобы перезапуск бота не обрывал активные интервью.

Сейчас bot.py создаёт Dispatcher() без storage, то есть используется MemoryStorage:
всё интервью живёт в памяти и теряется при каждом деплое на Railway. Существующий
SessionCheckpointMiddleware пишет чекпоинт в SQLite по пути reports/app_data.sqlite3,
но на Railway это эфемерный диск: если том не подключён, файл исчезает вместе с контейнером.

Что сделать:
  1. Подключить aiogram RedisStorage, если задана переменная окружения REDIS_URL,
     и оставить MemoryStorage как запасной вариант для локального запуска.
  2. Путь к SQLite (APP_DB_PATH) вынести так, чтобы он указывал на смонтированный том
     Railway, если переменная задана.
  3. Написать тест, который проверяет: при заданном REDIS_URL выбирается RedisStorage,
     без него — MemoryStorage.

Критерий приёмки: pytest tests -q → 0 failed; при заданном REDIS_URL бот стартует
на Redis-хранилище.
```

В Railway Redis добавляется в один клик через Add Service.
